# Plan: seller agents in the cloud

Move the three seller agents (Barolo, Sardinian, French) from laptops to
Kubernetes, in the slim-dev environment that runs the SLIM node
(comn-dev-use2-1). The buyer and the A2A CLI stay on laptops and reach the
sellers through `oidc.slim.outshift.io`.

Status: proposal. Two decisions are open (see the end).

## Shape

```
comn-dev-use2-1, namespace slim-dev (Argo project slim-dev)
 ├─ Deployment barolo-supplier     ┐ one image (agentcon-supplier)
 ├─ Deployment sardinian-supplier  ├ per seller: inventory, did:web key, SPIFFE X.509-SVID
 └─ Deployment french-supplier     ┘ connect to slim-dp's SPIRE-mTLS listener

laptops: buyer + a2a CLI (did:web) → oidc.slim.outshift.io → the same SLIM node
agents.slim.outshift.io: did.json per agent + JWKS (public ingress, static)
```

Sellers only dial out to SLIM, so they need no ingress. The only public URL is
the static did:web host, which serves public keys.

## Identity: SPIFFE inside, did:web outside

Agents are authenticated **internally with SPIFFE** and **externally with a
did:web**.

| Job | Identity | Trust anchor |
|---|---|---|
| **Inside the cluster:** connect to the SLIM node | the pod's SPIFFE **X.509-SVID**, on slim-dp's mTLS listener | SPIRE (trust domain `dev.ads.outshift.io`) |
| **Outside:** application identity that peers verify (MLS) | the agent's **did:web**, e.g. `did:web:agents.slim.outshift.io:agentcon:barolo-supplier` | control of the `agents.slim.outshift.io` domain and its TLS certificate |

### Why did:web, not did:key

A did:key is self-certifying: it proves possession of a key, not who holds it,
and anyone can mint one. Trusting it means pinning keys by hand
(`trust.jwks.json` today). A did:web resolves to a DID document published on a
domain, so only whoever controls that domain can say which key belongs to which
agent. Keys can rotate without changing the DID (or the SLIM name id, which
derives from it).

JWT-SVIDs are not an option outside the cluster: dir's SPIRE has no OIDC
discovery provider (`iss = https://oidc-discovery.dev.ads.outshift.io` does not
resolve), so laptops cannot verify them.

### Published documents (public keys only)

Served by a small static web server behind the cluster's public ingress
(`className: nginx`, cert-manager `letsencrypt`, external-dns under
`slim.outshift.io`):

| URL | Content |
|---|---|
| `https://agents.slim.outshift.io/agentcon/<agent>/did.json` | the agent's DID document: its Ed25519 key as a `JsonWebKey2020` verification method |
| `https://agents.slim.outshift.io/.well-known/openid-configuration` | `issuer` and `jwks_uri`, for SLIM's `autoresolve` |
| `https://agents.slim.outshift.io/.well-known/jwks.json` | every AgentCon agent's public key, `kid` = the agent's did:web (SLIM's signer stamps `kid = sub`) |

Agents covered: the three sellers in the cluster, and the laptop buyer and CLI.
Nothing secret is published.

### SLIM configuration (every agent)

Generated by `tools/slim/slim_identities.py --did-web agents.slim.outshift.io/agentcon OUT_DIR CLIENT_JSON agntcy/agentcon <agents>`,
which also writes `OUT_DIR/site/` (the files to publish):

```yaml
identity_provider:            # signs this agent's tokens
  type: jwt
  claims: { issuer: "https://agents.slim.outshift.io", subject: "did:web:agents.slim.outshift.io:agentcon:barolo-supplier", audience: ["agntcy/agentcon"] }
  key: { type: encoding, algorithm: EdDSA, format: pem, key: { file: /var/run/secrets/identity/key.pem } }
identity_verifier:            # verifies peers' tokens
  type: jwt
  claims: { issuer: "https://agents.slim.outshift.io", audience: ["agntcy/agentcon"] }
  key: { type: decoding, algorithm: EdDSA, format: jwks, key: { file: <the published jwks.json> } }
  subject_binding: enforce
```

- **Default: the published JWKS as a file, with `subject_binding: enforce`.** A
  token's `sub` must be the DID of the key that signed it, so no listed agent
  can claim another's DID. The file is the one the domain publishes; laptops and
  pods fetch it from `https://agents.slim.outshift.io/.well-known/jwks.json`.
- **Option: `--verifier autoresolve`** (`key: { type: autoresolve }`): SLIM
  fetches the issuer's discovery document and JWKS itself. Simpler, but SLIM
  applies `subject_binding` only to static trust lists, not to fetched keys.
- **Pin the issuer** in both modes. Without `claims.issuer`, `autoresolve` would
  accept any issuer that serves a JWKS.

Tested on a local node, with the site served at `http://localhost:8099`
(loopback is the only place SLIM accepts `http`):

| Case | Result |
|---|---|
| Barolo supplier and CLI, default JWKS verifier | quote returned |
| Another agent's key claiming Barolo's DID | rejected by the CLI: `token invalid` (`InvalidSignature`), since `kid = sub` selects Barolo's key |
| `--verifier autoresolve` | quote returned; SLIM fetched `openid-configuration` and `jwks.json` from the issuer |

### Private keys

- **Sellers:** each seller's Ed25519 private key comes from Vault through an
  ExternalSecret, mounted as a file (mode 0400) at `/var/run/secrets/identity`.
  Vault namespace `eticloud/apps/phoenix`, KV v2 mount `secret`, path
  `dev/agntcy/slim/agentcon-sellers`, one property per seller
  (`barolo-supplier-key`, `sardinian-supplier-key`, `french-supplier-key`),
  through ClusterSecretStore `vault-eticloud-apps-phoenix`. Each seller's
  ExternalSecret reads only its own key; the Azure credential is a separate
  secret (`dev/azure-ai`). The keys match the published
  `did.json` and `jwks.json` (cisco-eti/agntcy-deployment#548).
- **Laptop buyer and CLI:** keys stay on the laptops; only their public keys are
  published.

### Discovery

The catalog entry (and, later, the agent-directory record) carries each
seller's did:web, so the buyer knows which DID to expect behind
`slim://agntcy/agentcon/barolo-supplier`. Unlike a did:key, a resolver can
confirm it: the domain says which key belongs to which seller.

### Caveat

The domain is a single point of trust: compromising its web server or DNS
compromises every identity on it. did:webvh (verifiable history) adds a
hash-chained log on top of did:web if that is ever needed.

### Node connection: SPIRE mTLS

- Endpoint: `https://slim-dp-slim-dev-argoapp.slim-dev.svc.cluster.local:46368`
  (write the `https://` scheme). It authenticates the connection with the pod's
  X.509-SVID (client `tls.source` and `tls.ca_source` of type `spire`) and checks
  no token. slim-dp's SVID carries DNS SANs for that service name, so rustls
  hostname verification passes; SLIM's client checks hostnames with a plain root
  store, not SPIFFE IDs.
- Set **`tls_version: "tls1.2"`** on the client. The listener is pinned to
  TLS 1.2 for the gateway's Envoy, and SLIM clients default to TLS 1.3 only;
  without this the handshake fails with `TLSV1_ALERT_PROTOCOL_VERSION`.
- Don't use port 46367, the old unauthenticated in-cluster port.
- SPIRE is dir's server (trust domain `dev.ads.outshift.io`). The pods need a
  ClusterSPIFFEID with className **`dir-spire`**; under any other class no SVID
  is issued, and nothing reports why. This already works in `slim-dev`: five
  `dir-spire` ClusterSPIFFEIDs select slim-dp, slim-control, the channel
  manager and both gateway Envoys there. The seller chart mirrors them:
  - `className: dir-spire`, a `podSelector` on the seller labels;
  - `spiffeIDTemplate: spiffe://dev.ads.outshift.io/ns/{{ .PodMeta.Namespace }}/sa/{{ .PodSpec.ServiceAccountName }}`;
  - the `csi.spiffe.io` CSI volume mounted at `/spiffe-workload-api`, socket
    `unix:///spiffe-workload-api/spire-agent.sock`.

## LLM: Azure OpenAI key from Vault

Sellers need an LLM only for natural-language requests; structured RFQs are
answered without one.

- **Credential (decided):** the multi-cluster demo's Azure OpenAI credential,
  in its own Vault secret: namespace `eticloud/apps/phoenix`, `secret/dev/azure-ai`
  (`remoteRef.key: dev/azure-ai`), latest version, properties `azure-openai-token`
  and `azure-openai-url` (the base endpoint, `https://<resource>.openai.azure.com/`).
  Agents need only the model name besides those two files. The endpoint serves
  `gpt-6-luna` (the model the local demo uses through Copilot), its dated
  version `gpt-6-luna-2026-09-22`, `gpt-4o` and `gpt-4.1`. The sellers pin
  **`gpt-6-luna-2026-09-22`**, so the model can't change between rehearsal and
  the talk; laptops keep `gpt-6-luna` through Copilot. No API version.
- **Delivery:** External Secrets Operator through ClusterSecretStore
  `vault-eticloud-apps-phoenix` (KV v2 at mount `secret`, so `remoteRef.key` has
  no `secret/` prefix; no namespace conditions, so `slim-dev` can use it), from
  an `ExternalSecret` template in the seller chart. The Secret is mounted as files
  at `/var/run/secrets/model/{api-key,base-url}`. The multi-cluster demo's
  original store, `vault-eticloud-apps-espresso`, does not exist on
  comn-dev-use2-1.
- **Supplier change:** read `MODEL_API_KEY_FILE`, `MODEL_BASE_URL_FILE` and
  `MODEL_NAME`, and set the Copilot SDK's bring-your-own-key provider in
  `SupplierAgent/src/inference.rs`:
  `SessionConfig::with_provider(ProviderConfig { type: "openai", base_url: <azure-openai-url> + "openai/v1", api_key, model })`.
  The endpoint's Azure v1 route is OpenAI-compatible: `GET /openai/v1/models`
  lists the models above, and `POST /openai/v1/chat/completions` with a model
  name works (probed against the endpoint). One chat call with the pinned model confirms it
  before the chart bakes it in.
  When no provider is configured, the supplier keeps today's Copilot behaviour
  for laptop runs.
- The key is never put in an environment variable dump, a log or a trace.

**Vault paths must be under `dev/`.** The phoenix ClusterSecretStore logs in with
this cluster's role `external-secrets-comn-dev-use2-1`, which can read only
`secret/data/dev/*`; anything else fails with `403 permission denied` and the
pods wait in `PodInitializing` for their Secret volumes.

## Image and chart

- **Image:** multi-stage Rust build into a slim glibc base (for example
  `gcr.io/distroless/cc`). The Copilot CLI runtime is bundled in the supplier
  binary, so no Node is needed; it extracts into `SUPPLIER_COPILOT_STATE` (an
  `emptyDir`). Published as a **public** GHCR image from the AgentCon repo; the
  cluster already pulls public `ghcr.io/agntcy/*` images, and a private one
  would need an imagePullSecret.
- **Chart:** published to GHCR (OCI) from the AgentCon repo. Its values live in
  agntcy-deployment at `applications/agentcon-sellers/dev/a/{config.json,values.yaml}`,
  with an entry in `applicationsets/slim/dev/applicationset.yaml`. The project's
  `sourceRepos` already allow `ghcr.io`.
- **Namespace:** `slim-dev`, the only namespace the Argo project allows. A
  separate `agentcon` namespace would need adding to
  `projects/slim/dev/slim-dev.yaml`.
- **Per seller:** Deployment (1 replica, modest requests: the node pool is small
  and has been CPU-full), ConfigMap (inventory, SLIM config), ServiceAccount plus
  ClusterSPIFFEID (`dir-spire`), ExternalSecrets (did:web private key, LLM key), probes on
  `/health`.

## Supplier changes

1. **Readiness reflects SLIM.** `slim_ready` is set once and never cleared, so
   `/health` reports SLIM as ready after the connection is gone.
2. **LLM provider from configuration** (above).
3. **SLIM client TLS from configuration:** SPIRE `tls.source` / `ca_source` and
   `tls_version`. The supplier already passes the config file's `client` section
   to SLIM, so this may need no code change; to be confirmed.

## Demo changes

- `catalog.json`: the cloud sellers keep their `slim://` names; their HTTP Agent
  Card URLs are not public, so the catalog needs the card served another way
  (for example over SLIM, or a copy in the catalog).
- `start-demo.sh`: a mode that starts only the buyer and uses the cloud sellers.
