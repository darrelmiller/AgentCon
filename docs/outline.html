AgentCon A2A v1 talk: outline (wine scenario)

25 minutes: 2 minutes for the opening and protocol layers, 20 minutes for the demo, and 3 minutes for A2A 1.1 and closing feedback.

0:00–2:00 Opening slides (both)

  • Slide 1 — A2A v1 Deep Dive: Extending the Protocol. One-line introductions.
  • Slide 2 — Agenda. "Two minutes on the protocol layers and how to extend them, twenty minutes working with agents that buy and sell wine, then three minutes on what's coming in A2A 1.1."
  • Slide 3 — One protocol. Three layers. Read across each row: what the layer defines, then how it can be extended. "The data model is the vocabulary: add metadata, structured payloads, and profiles without changing core fields. Operations define behavior: extensions can add methods and interaction flows. Protocol bindings map those operations and data to a concrete protocol: a custom binding adds a new mapping while preserving their semantics."
  • Slide 4 — Demo time! "Working with agents that buy and sell wine."
  • Promise: "In 20 minutes Luca's seller agent will come off the public internet, and my agent will still be able to buy from it. That's what a custom protocol binding gets you, and you don't have to change the spec to get it."
  • Switch from Edge to a clear GitHub Copilot CLI instance; leave the slides parked on slide 4.

2:00–4:00 Discover and send an RFQ in natural language (Darrel)

  • Start with a clear GitHub Copilot CLI instance.
  • For the baseline, start with the seller's Advertise structures and the buyer's Native structures disabled.
  • Enter: "Can you find an agent to help me buy wine?"
  • GitHub Copilot uses the AI Catalog CLI to find the agent.
  • Stay in the CLI and proceed directly to the quote request.
  • Enter: "Can you get me a quote for 15 cases of 2019 Barolo to be shipped to Montreal, Quebec"
  • Let the agents obtain the quote, then switch to the dashboard.

4:00–7:00 Explain the dashboard (Darrel)

Follow one quote request through the dashboard rather than touring every control. Use these three minutes to connect the live interaction to the protocol layers on slide 3.

  1. Orient: Buyer, Conversation, Seller. "Copilot is talking to our buyer agent. The buyer talks to the wine seller. These are the actual exchanges, not a generated summary." Establish who is communicating.
  2. Explain the Buyer Agent and Seller Agent information panels. Point out their endpoints, availability, and LLM call and response-time totals. Keep the Agent Cards closed for now; save them for the transition into structured content.
  3. Select the outgoing quote request, then the reply; use Stream Inspector → Content. "The request and response carry natural-language text inside message parts." Point to the actual wine, quantity, and destination. Connect to the data model: messages and parts.
  4. Expand the relevant Buyer task and Seller task. "Each agent manages its own task. Here are their IDs and observed states." Do not imply that they share one task ID. Connect to the data model: tasks, and operations: work initiated by sending a message.
  5. Switch the selected request to Wire. Identify the operation and its concrete representation. "This is how the operation and message are mapped onto this protocol binding." Use the inspector's binding label for this exchange, not the setting for the next request. Connect to operations and protocol bindings.
  6. Finish by opening the seller's Agent Card. "This describes the agent's capabilities and the interfaces it supports. Right now, it only advertises text/plain." Point to the supported content types. Connect to the data model: Agent Card, then use this as the before-state for enabling structured content in the next section.

Briefly point to LLM calls and LLM response time on each agent: "Remember these numbers; we'll compare them with the structured exchange later." These are cumulative since Clear. Model-response time is not total transaction time, and the dashboard does not display token counts. Respect any partial or not-reported indicators.

The Agent Card is the final reveal of this walkthrough and the transition into structured content. The seller's switch is labelled Advertise structures; the buyer's is Native structures. Keep the seller-first, buyer-second sequence. Save binding selection and the authorization extension for later.

7:00–9:00 Enable seller structured content (both)

  • Close the Agent Card and enable Advertise structures on the seller. Leave the buyer's Native structures disabled so the audience sees one change at a time.
  • Reopen the seller's Agent Card to show how it changed: compare the earlier text/plain-only advertisement with the newly advertised media types and schemas for wine RFQs, quotes, and purchase orders.
  • Repeat the quote for 15 cases of 2019 Barolo shipped to Montreal, Quebec. Inspect the structured parts rather than only the natural-language summary.
  • "The seller now advertises structured content. The buyer can learn the advertised schema, but that adaptation can still involve the model."
  • Explain that a media type identifies a format; advertising it alone does not teach an unknown schema. The agents need an agreed, versioned schema.

9:00–11:00 Enable buyer structured content (both)

  • Open the buyer's Agent Card and show its current content types. Close it, enable Native structures on the buyer, then reopen the card to show the change. Keep the seller's structured content enabled.
  • Repeat the same quote and inspect the typed RFQ and quote parts. Compare the additional LLM calls and model-response time with the previous runs; the dashboard totals are cumulative.
  • "Now the buyer has native support for these structures too. The structured exchange is faster and more deterministic, so we'll keep it enabled for the purchase."
  • Distinguish the natural-language CLI instruction from the typed agent-to-agent exchange. Text input can still invoke Copilot; do not claim that the entire interaction uses zero inference merely because the switches are enabled.
  • Only claim zero model calls for a measured deterministic segment when the observed counts support it. Keep discovery, schema learning, and natural-language interpretation separate from that claim.
  • Concepts: advertised media types, agreed profiles, and typed parts. Local demo profiles are defined in SupplierAgent/schemas/wine-v1.schema.json; its unregistered application/vnd.agentcon.demo.wine-*.v1+json types must be agreed with Luca, not assumed interoperable from advertising alone.

11:00–14:00 Buy it: purchase and age check (both)

  • Keep structured content enabled on both agents. This puts the faster, more deterministic interaction in place before the live purchase and wallet flow.
  • "Buy it." Task goes to TASK_STATE_AUTH_REQUIRED.
  • QR code appears; Darrel scans it with his phone wallet.
  • Luca shows his verifier received "over 21" and nothing else.
  • Task resumes and completes. Inspect the structured purchase result and its artifact.
  • Explain the extension from the card: purpose, declaration, where its data goes.

14:00–22:00 Private endpoints over SLIM (Luca, then Darrel)

  • Set up the why: a public HTTP endpoint is attack surface, and a small seller doesn't want to run ingress, a gateway and certificates just to take orders. A custom binding takes the endpoint off the public internet.
  • Luca moves to a phone hotspot and shows there's no public IP or open port.
  • His card lists a SLIMRPC interface; Catalog entry advertises a SLIM name.
  • Same order. App logic unchanged, binding different.
  • Show the routing node forwarding encrypted traffic it can't read.
  • Concepts: custom bindings, why the layers matter.

22:00–25:00 Wrap-up (both)

  • Return briefly to slide 3. Map the demo back to the framework: structured wine payloads and profiles extend the data; the authorization extension adds an interaction flow; SLIMRPC supplies a custom protocol binding. Distinguish these from changes to the core specification.
  • Advance past slide 4 to slide 5 — Where we're going next, and leave it on screen for the close.
  • "For A2A 1.1, we're working on a task timeline to replace history: a record of how the task unfolds."
  • "We're also working on letting clients send artifacts as well as receive them, enabling bidirectional streaming."
  • Present these as work in progress, not capabilities already available in v1.
  • Links to the experimental repos; ask for feedback.
  • Close: "Help shape A2A 1.1. Bring your use cases and feedback."

Open decisions

  • Buyer implementation: GitHub Copilot CLI drives the official a2a CLI to call the local C# BuyerAgent A2A service. That service uses the GitHub Copilot SDK as its harness and the official .NET A2A SDK to call the seller. No Microsoft Agent Framework in the initial implementation.
    • Already there: --data-part for structured orders; --wait stops on auth-required; pluggable transports (a2a-transport-<name> on PATH).
    • SLIM: a SLIMRPC plugin was built in a2a-rs (a2aproject/a2a-rs#296, closed); docs still open (a2aproject/a2a-rs#297). Verify it round-trips and assess reuse from the .NET buyer before building our own. The buyer currently implements JSON-RPC only.
    • Catalog: the a2a CLI has no AI Catalog resolution (optional in the CLI spec, not implemented), so the buyer resolves it: its search_supplier_catalog tool searches the configured catalog (default catalog.json) for A2A Agent Card entries and select_supplier selects one by catalog identifier. The local Rust seller now has a live card entry on port 6000; Luca's eventual card also goes into the catalog, not buyer configuration.
    • Local seller baseline: SupplierAgent uses official A2A and Copilot Rust SDKs for NL quotes and simulated purchases, plus deterministic typed RFQs/orders. Purchases require a task-bound OID4VP presentation to the issuer-hosted verifier; quotes remain open. This verifies a signed demo claim, not real age. SLIM remains unimplemented.
    • Wallet hand-off: the buyer relays the experimental extension's authorization request and the issuer-hosted QR page. After wallet approval, continue the same seller purchase task; approval never comes from model or user assertions. The buyer sends the extension URI in the seller's A2A-Extensions header. Actual Sphereon presentation interoperability still needs a phone scan.
    • Wallet installed: Sphereon 0.8.0. Upstream 0.7.0 release notes advertise OID4VP 1.0 Final and OID4VCI draft 15; the 0.8.0 source includes SD-JWT and DCQL support. Darrel confirmed successful QR issuance and credential receipt on his phone on October 10, 2026. OID4VP presentation and verifier interoperability remain untested.
    • Phone issuer: IssuerAgent implements demo OID4VCI pre-authorized issuance at https://agentcon-issuer.azurewebsites.net. Admin-created QR offers are short-lived and single-use; credentials are signed for the phone's proof key. Live deployment and phone receipt are confirmed; subsequent OID4VP presentation remains to be checked. Azure uses a dedicated Linux B1 App Service plan in darrmi_personal.
